# 公開 API の契約・利用シナリオのレビュー案

作成日: 2026-11-20。第1〜150問の合意を、呼び出し側から読める形にまとめる。根拠は[回答記録](questions.md)、ゲームの概念モデルとルール判断点は[設計案](design.md)、公式根拠の取得状況は[ルール差分](rule-differences.md)を参照する。

**confirmed requirement** は回答で合意した契約、**candidate design** は今回の整理・提案、**unresolved question** は未確定の判断である。この文書全体の承認、具体的な Rust の型・シグネチャの確定、実装開始を意味しない。説明用の項目名は公開 schema ではない。第116問により Rust API の命名は中国語ピンイン中心とし、旧用語集の回収・参照は必要になった段階に限る。12節の候補名のため main の固定版を部分参照し、旧ファイルの復元・定義の自動採用はしていない。

## 1. 最初の提供範囲

### Confirmed requirement

- Rust API を先に提供する。Python API は将来の検討対象とする（第97問）。
- 最初の公式プリセットは雀魂の四人段位戦とし、東風戦・半荘戦を含める。適用版・細則は別途公式根拠で照合する（第62・63・98問）。
- 利用側が Agent と牌譜出力先を渡し、LizhiSim が複数卓の進行・互換な要求の集約・応答の照合を管理する（第1〜3・24問）。
- 同期型の実行 API は対局群と必要な終了処理の決着まで待ち、結果を返す。内部の Agent の回答は非同期とし、Future 方式を基本とする（第18・30・37・106問）。
- 通常の独立対局の実行に加え、比較グループの配置を展開するデュプリケートを扱う（第74問）。
- 標準の牌譜ファイル保存・読込みと、記録した入力・行動を使う replay を提供する（第27・105問）。
- 最初の統計補助は順位別回数とする。報酬と段位ポイントへの換算は利用側が担当する（第34・64・65問）。
- 一つのライブラリ crate から始め、将来の細分化を見据えて module の責務・依存方向を整理する（第101問）。

大会・シーズン・トーナメントの管理、Epsilon 型の局面分岐、production API での任意の途中局面指定は初期対象に含めない。開発用の局面設定は単体・リグレッション検証に用いる。外部の実牌譜取得・逐次照合は後続とする（第32・36・100問と追加のスコープ判断）。

## 2. 利用側が準備するもの

### Confirmed requirement

| 入力の概念 | 契約・用途 | 主な根拠 |
|---|---|---|
| 解決済みのルール | 一回の実行は一つのルールに統一する。プリセットからの個別変更を含め、LizhiSim が提供する値・振る舞いの選択肢を組み合わせる | 第31・70・71問 |
| 対局の開始条件 | 最初の局を配る前から開始する。開始持点は参加者ごとに指定可能。通常対局の初期席順は内部でランダムに割り当てる。固定席・指定牌山・途中局面からの実行は別 API に分け、別 API の初期提供範囲は未決とする | 第33・35・36・142問 |
| 比較対局の指定 | 比較グループ・席数配分・比較セット数を渡す。一グループに一つの Agent インスタンスを対応させる | 第74・93問 |
| Agent | 合法手から行動を選ぶ。推論・モデル入力変換・通信・内部の方策更新を担当する | 第2・7・8・38問 |
| 牌譜出力先 | 完了・中断した対局の完全情報の記録を処理する。標準の保存処理に加え、独自実装も利用できる | 第22・24・26・105問 |
| 実行全体の seed | 対局識別と牌山共有の識別を区別して、実行順に依存せず乱数入力を導出する | 第51・52・74・75問 |
| 実行の上限・期限 | 同時進行対局数、Agent ごとのバッチ件数・集約待ち時間、意思決定・通知・出力の期限を指定する | 第46〜50・85・89〜92問 |

LizhiSim はすべての開始条件と共通設定を開始前に検証し、不正があれば対局群を開始しない。将来の Agent 応答の正しさまで事前検証する契約ではない（第66問）。

意思決定・Agent 通知・牌譜出力の必要な有限期限は、コア API で明示指定する。規定値の補完は文書例や設定ファイルからの変換側の責務とする。出力受付待ちにも別の有限期限を設ける。第124問により、意思決定バッチの Agent 受付枠の空き待ちにも、受渡し後の処理期限とは別の有限期限を設ける。第127問により、通知が必要になってから Agent に渡すまでの待機にも別の有限期限を設ける。具体的な入力形式・値の範囲・受付待ち期限の指定方法は未決である。

同じ Agent・牌譜出力先インスタンスを、並行する別実行で共有する契約は初期対象に含めない。別インスタンスが内部で共通の推論・保存サービスを使うことは可能とする（第99・102問）。

第142問により通常対局の席順は内部でランダム化し、固定席・指定牌山・途中局面からの実行は別 API とする。別 API の初期提供や、部分固定牌山の生成・局面検証の具体契約は未決である。デュプリケートの比較配置の内部展開、開発用局面設定、記録入力からの replay はこの通常 API と区別して維持する。

## 3. 対局実行の正常系

### Confirmed requirement

1. 利用側が開始条件・設定・Agent・出力先を準備し、同期型の実行 API を呼ぶ。
2. LizhiSim が開始前検証を行い、同時進行数の範囲内で対局を開始する。各対局・観測座席へ専用の開始通知を送り、その処理完了後に当該対局・座席の意思決定要求を渡す。
3. LizhiSim が合法手を計算する。一つだけなら要求を省略し、唯一の行動で進め、その経過を記録する。複数候補なら、互換な他卓の要求と集約して Agent の受付範囲内で渡す。
4. Agent が Future 方式で非同期に回答する。その間も独立した他卓を進める。バッチの回答は全件そろってから受け取り、要求識別情報の対応を検証してから行動を適用する。
5. 局末・対局終了は、意思決定がなくても Agent へ通知する。完了・中断した対局の牌譜を出力先へ渡す。終了通知・出力待ちの対局も同時進行数に含め、必要な終了処理の決着後に枠を空ける。
6. 実行を終え、対局番号順の結果一覧と対象となる統計を返す。実行全体の正常完了と、全対局の成功は区別する。

根拠: 第3・9・11・14〜19・30・37・50・55・56・82・85・88・103・106問。

通常、同じ対局・観測座席の通知と要求は先行処理の完了後に次を渡す。第112問により、中断通知だけは先行する非同期処理の完了を待たずに渡せる。同じ Agent の呼び出し入口はすべて直列とする一方、受付範囲内で別卓・別席の処理や複数バッチの完了待ちを重ねられる。牌譜出力先も入口の直列化と受付後の処理完了を区別する（第15・16・73・86・89問）。

第48・49問の件数上限または集約待ち時間上限での送信に加え、第126問により、追加の互換な要求を集められる見込みがない場合は上限未満でも時間上限を待たずに送信する。残り3卓すべてが回答待ちで上限64件なら、Agent が受付可能な場合は3件で送信する。受付不能なら受付待ち・期限切れの契約に従い、早期送信を理由に受付範囲を超えない。追加要求の見込みの具体的な判定条件は未決である。

## 4. Agent との受渡し

### Confirmed requirement

| 情報・操作 | 契約 |
|---|---|
| 要求の文脈 | 対局・観測座席・要求を識別できる。共有 Agent 全体で一つの座席状態や履歴位置を使わない |
| ルール | Agent は、プリセット変更を含む実際の解決済み設定を参照できる |
| 入力 | 現在の観測状態、対局開始からの観測可能な全履歴、新規部分の開始位置、合法手一覧を渡す |
| 新規部分の基準 | 同じ対局・座席で処理完了した要求・通知の履歴末尾を基準とする |
| 入力の有効性 | 非同期処理中に加え、正常完了後も Agent が保持する間は要求時点の有効性・不変性を維持する。受付時の全コピーは必須にしない（第59・115問） |
| 回答 | 要求識別情報と、選んだ行動そのもの、または要求単位の処理エラーを返す。回答一覧の順序は自由 |
| 抽選 | 行動を確率的に選ぶ場合も Agent 内部で行う |
| 経過の配送 | 開始通知、意思決定要求、局末・対局終了・中断の通知を用いる。すべての観測イベントの即時配送は要求しない |

根拠: 第7・10・14・19・54・55・58〜60・72・82・106問。各通知の具体的な入力・完了表現、履歴イベントの粒度は未決。

合法手は固定の行動番号・マスクではなく、その局面で選べる行動の一覧とする。同じエンジン・ルール版の同じ状態では順序も再現する。具体的な並び順は未決。立直と宣言牌は一行動、チー・ポンとその後の打牌は別要求とする。手切り・摸切り、赤牌・通常牌は区別し、手牌内の同種・同属性の牌の個体差では打牌候補を増やさない（第8・54・67〜69・80・81問）。

同じ応答窓に要求した全席の回答を待ち、到着順ではなくルールで競合を解決する。他家の未公開選択を同じ窓内の後続要求へ漏らさない。異常時まで無限に全席を待ち続ける契約ではない（第53問）。

**C-API-01（第107問で採用）: Future の完了結果としてバッチの回答一覧を受け取る。** LizhiSim は完了結果から回答一覧を受け取り、要求識別情報の対応を検証してから適用する。共有の回答領域への書戻しを完了通知する方式を基本の公開契約にはしない。Agent 内部の実装方法は制限しない。具体的な型・シグネチャは引き続き未決である。

第108問により、Agent への通知・牌譜出力も Future の完了結果で成功・失敗を返す。通知は行動回答を求めない。処理をその場で終えて完了済みの Future を返す実装も扱え、同じ具体型を全操作に強制しない。出力の完了範囲は出力先の契約で定め、受付と完了の区別・既存の期限・失敗範囲は維持する。

第109問により、LizhiSim の進行・Future の完了待ちに必要な非同期実行基盤は内部で管理する。利用側は同期型の実行 API を呼べばよく、LizhiSim 用のランタイムの準備・指定は求めない。Agent 内部の推論・通信基盤は Agent 側の責務とし、具体的なライブラリや実行器は未選定である。

第110問により、期限切れ・利用者停止時には Agent・出力先へ協調的な取消を伝える仕組みを含める。伝達は処理の停止・完了・資源回収を保証せず、実施済みの書込みも巻き戻さない。有限期限・既存の失敗範囲と参照中データの有効性は維持する。具体的な伝達手段・単位と Future の保持・破棄、遅延完了・中断通知の順序は未決である。

第111問により、Agent の意思決定バッチの取消は最初はバッチ全体を単位とする。一部の対局が中断しても有効な要求が残る間は処理を続け、不要な回答は適用しない。全件が不要になれば取消を伝える。要求単位の取消伝達は初期対象に含めず、バッチ全体の回答受付と要求識別情報の照合は維持する。通知の取消単位は第129問で通知1回ごとに確定。牌譜出力の取消単位は第130問で出力1件ごとに確定。中断通知の順序は第112問の例外に従う。

第129問により、通知の取消は通知1回ごとを単位とする。開始・局終了・対局終了・中断の通知ごとに独立した取消状態を渡し、先行通知の取消状態を後から送る中断通知へ引き継がない。第113問の受付時に取消情報を渡す方式を使う。取消の伝達と処理停止・完了・資源回収は区別し、参照中の入力の有効性を維持する。

第112問により、中断通知だけは同じ対局・座席の先行する非同期処理の完了を待たずに渡せる。入口の直列化は維持し、受付後の残存処理との重複を許す。Agent が残存処理と状態整理の整合性を管理し、参照中の入力の有効性を維持する。通常の要求・局末・対局終了通知には完了順の保証を維持し、中断通知には有限期限を適用して再試行しない。

**C-API-02（第113問で採用）: 受付時に、処理ごとの取消状態を確認・待受できる情報を渡す。** LizhiSim が取消を伝え、受取側が Future の処理やバックグラウンド処理の整理に用いる。意思決定は第111問どおりバッチ全体を単位とし、取消専用の trait 呼び出しを基本方式にはしない。具体的な型・所有と共有・待受方法は未決である。

第114問により、長い同期推論・同期 I/O は Agent・出力先の実装側で非同期化し、受付や Future の進行を長時間ブロックさせない。軽い同期処理を完了済み Future で返す方式は維持する。LizhiSim が任意の同期処理を包む汎用アダプターは初期範囲に追加しない。標準出力先の提供は維持し、その実装でも必要な非同期化を行う。

第115問により、Agent は正常完了後も入力を保持できる。保持量・期間・解放時期は Agent 側で管理し、LizhiSim が全対局の入力を自動的に蓄積するものではない。同時進行対局数の上限では完了後の長期保持分を制限できず、全件保持し続ければメモリは増える。具体的な所有・共有・保持単位と回収方法は未決である。

### Unresolved question

Future の Box 化・Send と必要データの独立保持は第136・138・139問で採用済み。具体的な型別名・ライフタイム表記・共有と回収、内部実行基盤の選定・配置は未決。受付での Agent の独占を処理完了まで継続させて複数バッチを受け付けられなくする設計は、合意した重複処理と整合しない。受付と Future の進行・完了、受渡し時刻の具体的な境界をレビューする必要がある。

通知・出力も Future の完了結果で成功・失敗を返すことは第108問で確定。Future の待機を打ち切ることと、推論・通信・保存を停止してデータを回収することも別の契約である。

## 5. 比較セット・乱数・記録

### Confirmed requirement

| 比較形式 | 一セットの配置数 | 完全な一セットで各グループが得る順位結果の件数 |
|---|---:|---|
| 1vs3 | 4 | 4件・12件 |
| 2vs2 | 6 | 各12件 |
| 各1席の4グループ | 24 | 各24件 |

グループ内の入替えを別配置として増やさず、一グループに対応する Agent は一インスタンスとする。統計は比較グループに属する全参加席の結果を合算する。全配置の最終順位が確定した比較セットだけを統計対象とし、不完全なセットは終了済み配置の分も含めて除外する。各対局の結果・牌譜は残し、除外を識別可能にする（第74・77・78・93問）。

同じセットで場を含む局番号・本場が一致する局には、同じ牌山を必要時に生成する。通常の山順と席別ツモ列は実験設定で選ぶ。席別の列が尽きれば、残り枚数が最多の他席の列の末尾から取得する。同数時の具体的な優先順、列の割当・山と王牌の整合の詳細は未決である（第75・76・94問）。

列の枯渇による取得は、どのツモでどの席の列から取得したかを発生ごとに完全情報の牌譜へ残す。対局結果には有無・回数を付け、Agent 向けの観測・履歴・通知にはこの識別情報を含めない。異なる行動列でも各席の全ツモが最後まで固定される保証はしない（第94・95・104問）。

各局の実際の牌山、採用した行動、ルール・取得方式と必要な意味版を記録し、replay は記録入力を直接使う。同じエンジン・ルール意味版では、対応する OS・CPU 間でも麻雀上の再現性を保証する。Agent の確率的選択、実時間や期限切れの発生、対局間の出力順は対象外とする。RNG・seed 導出・shuffle は未選定である（第7・27〜29・51・76・96問）。

標準の保存・読込みから replay まで提供し、第117問により当初は人間可読な JSON 系を基本とする。第118問により標準出力は一対局一ファイルを基本とし、第119問により無圧縮・圧縮の双方を選択できる。圧縮によって再生に必要な情報は省略しない。具体的な schema・符号化・ファイル名・ディレクトリ構成・圧縮方式や既定値、一時ファイルや書込み完了の扱いは未決。第29問を越える将来版での全過去記録の互換性は確定していない（第105問）。

第120問により、標準牌譜は入力・行動・進行イベントを基本とし、途中状態を replay で再構築する。毎意思決定時の状態一式のスナップショットは初期の標準記録に追加しない。実際の牌山・採用行動・局末結果・中断・列枯渇の記録等と、Agent による要求入力の保持は維持する。具体的な schema・照合項目は未決である。

第121問により、通常の replay は非互換な版では拒否し、牌譜と互換性のある版では許可する。版の相違だけで一律には拒否しない。非互換な版での再実行は、利用者が明示的に選ぶ開発・比較用途として区別する。保存形式を読めることと進行・精算等の意味を再現できることは分けて検討し、互換性の判定基準・識別方法・対応範囲は未決である。第29問の再現保証と、将来の全過去記録への互換性を保証しない方針は維持する。

第122問により、通常再生の互換性は保存形式とゲーム進行の意味の両方を対象とする。読込み可能という条件だけでは足りず、合法手・状態遷移・精算等の再生互換性を維持する版を許可する。形式を変更しない修正でも結果が変わる場合は、明示的な開発・比較用途として扱う。互換性の識別・宣言・検証方法と対応版の範囲は未決である。

四人・三人で進行の違いを型に反映することと、scheduler・取消・牌譜出力・共通の牌操作等まで二重実装することは別である。共通 mechanics は再利用し、必要な場所で人数ごとの振る舞いへ分岐する。型を分けるだけで特定のルールを数値設定だけに限定したり、他の確定要件をなくしたりしない。高スループットへの効果は未測定である。

### 既存契約との整合で確認すること

1. **通常の独立対局と、全員独立のデュプリケートを区別する。** 第74・78問には、各1席の4グループを同じ牌山で24配置に展開する要件がある。第145問で実行方式と構成を分け、4者独立のデュプリケートも維持することを確認した。具体的な variant 名と各入口の入力・結果の表現は未決である。
2. **論理枠と本体を分ける。** 第14問は同じ Agent インスタンスの複数卓・複数席での共有を認めている。4要素の配列を &mut Agent の直接参照で構成すると、同じ本体を複数要素へ重複配置できない。[Rust の可変参照の制約](https://doc.rust-lang.org/book/ch04-02-references-and-borrowing.html)によるものであり、入口を後から直列に呼ぶだけでは配列の構築を可能にしない。第146問で、論理枠の対応を固定長配列にし、本体を一度だけ登録して参照する方式を採用した。第14問の共有範囲は維持する。
3. **Agent・記録との境界を整える。** 入口だけ人数別にして観測や合法手・ルール・結果に不整合を許す形にはしない。第148問で Agent の入出力と登録も人数に応じた型にすることを採用した。Agent trait は人数型をパラメーターにすることを第149問で採用した。具体的な型の表現は未決である。三人・四人の記録でも再生に必要な人数・ルール・形式を識別する。初期公式プリセットを雀魂四人段位戦とする範囲は変えない。
4. **比較単位の再現性・統計を維持する。** API を分けても、同じ比較セット・局条件での牌山共有、全配置が完了したセットだけを集計する方針、グループ別の順位件数を維持する。1vs3は4配置、2vs2は6配置であり、1vs2を同じ重複除去の意味で扱う候補では3配置となる。参加者順を固定席指定と混同しない。

この整理は設計レビューであり、型・API 分離の具体方式の一括採用や実装開始の許可ではない。最初のテストは再検討中とし、不正入力を用意することを目的に API を弱めない。
### 通常実行とデュプリケートの別 API（第145問で採用）

**Confirmed requirement**: 第145問で、通常実行とデュプリケートを別の公開 API にすること、Agent 構成を enum とすること、内部実装を共有することを採用した。下記の一入口との比較は判断の根拠であり、一入口方式は基本 API として採用しない。具体型・識別子は引き続き未決である。

「通常実行／デュプリケート」は実行方式であり、「4者独立／1vs3／2vs2」は Agent の構成である。4者独立の Agent 構成でもデュプリケートなら24配置を展開する。第147問で、通常実行でも1vs3・2vs2・三人の1vs2を指定できることを採用した。以下で通常実行とは、比較セットの配置展開・牌山共有を行わず対局を実行する方式を指す。

| 契約 | 通常実行 | デュプリケート |
|---|---|---|
| 実行数の指定 | 対局数を指定する候補 | 比較セット数を指定し、構成から配置数を展開する |
| 席と牌山 | 通常対局の初期席順は内部でランダム化し、牌山を生成する | 構成に応じた席配置を重複なく展開し、セット内の同じ局条件で牌山を共有する |
| 結果の対応 | 各対局と参加者の結果 | 各対局の結果に加え、比較セット・配置・グループの対応 |
| 順位統計 | 通常の対局結果に基づく集計 | 全配置の最終順位が確定したセットだけを統計対象とし、不完全なセットの結果は統計から除外する |

一つの bool だけで切り替えると、対局数とセット数の取り違え、片方でしか意味のない入力・結果の組合せを別途防ぐ必要がある。enum の variant ごとに必要な入力を持たせれば同じ入口でも表現可能である。その場合、結果側にも variant を使う等により意味を対応させられる。ただし戻り値を mode ごとに型で分けたい場合は、単一の実行時 enum だけではなく追加の型設計が必要になる。

**第145問で採用した方針**: 今回は呼出側が実行時に方式を切り替える必要が少ないという意向と、入力・集計・結果の意味の違いから、通常実行とデュプリケートは別の公開入口とする。人数別の型分離とは両立させる。Agent 構成は閉じた enum で表し、通常実行でも人数に対応するすべての合意済み構成を指定できることは第147問で確定した。scheduler・Agent バッチ化・一対局の mechanics・取消・牌譜配送は内部で共有する。具体的な公開関数名・戻り値型・enum 名は未決である。

共通の1入口と入力 enum を採る案も成立するが、利用側の結果の取出し・型の対応を含めて比較する。どちらの方式にも、公開入口の違いだけからスループットの優位を主張しない。将来の設定ファイルからの切替が必要になれば、外側で enum を受けて各入口へ振り分ける層も候補となるが、初期提供へ先行追加しない。
### Agent の配列と本体共有（第146問で A を採用）

**Confirmed requirement**: 第146問で A を採用した。Agent 本体を一度登録し、構成内の固定長配列には登録先を参照する値を入れる。同じ本体を複数枠で共有し、論理グループと本体の同一性は分ける。B は基本方式として不採用であり、下表は比較経緯である。

| 案 | 配列で表すもの | 既存の共有契約との関係・利用側の手間 |
|---|---|---|
| A：本体を一度登録し、構成内の配列には登録を参照する値を入れる | 独立の4枠・3枠や、比較の2グループ枠 | 同じ登録先を複数枠から参照でき、第14問の本体共有を維持できる。利用側に登録と対応付けの準備が加わる |
| B：構成内の配列へ本体の可変参照を直接入れる | 各論理枠に一つずつの別本体 | 登録段階を省けるが、同じ本体を複数の論理枠へ渡すことはできない。第14問の共有範囲を変更する必要がある |

A は配列化を取り消す案ではなく、固定長の論理枠と、その参照先の実体を区別する案である。登録の具体型・所有・参照方法は未決。同じ本体を参照していても、論理グループの同一性や統計を自動的に併合せず、第74・78問のグループとして扱う。

B でも1vs3の3席を一つの基準 Agent へ、2vs2の各2席をそれぞれの Agent へ内部で対応させることは可能である。一方、独立4枠すべてを同じ本体で処理することや、比較の二つの論理グループで同じ本体を使うことは直接表せない。別本体の内部で同じモデル・推論基盤を共有する方式は、LizhiSim が同じ Agent インスタンスへ要求を集約する契約と同一ではない。

どちらも本体の所有を呼出側に残し、同じ本体の入口を直列に呼ぶ契約と、受付後の Future の重複処理は維持する。第146問で A を採用し、既存の共有範囲を維持する。具体的な登録・参照型と借用の表現は未決である。最初のテストを選ぶためだけに登録参照の不正を表せる API を先に導入しない。

## 14. 公開 API を起点とする TDD と内部テスト

### 既存方針の適用と第150問の提案撤回

仕様駆動で公開 API の契約からトップダウンに進めることは既存の confirmed requirement である。第150問の「内部の配置生成を最初に単体テストする」案は、この方針に対して内部部品を先行させていたため撤回する。公開 API に出ない処理にも単体テストの価値はあるが、それを最初の TDD や実装開始の必須条件とはしない。

### Candidate design

1. 公開 API の入力・出力・外部から観測できる振る舞いを、利用例と受入シナリオで具体化する。
2. 採用したシナリオを確かめるテストを起点に、実現に必要な内部の責務へ進める。内部全体の実装を事前に完成させることは要求しない。
3. 配置生成・合法手判定・精算等の内部処理に、個別に検証すべき複雑さや境界条件が現れた段階で、必要な単体テストを追加する。

例えばデュプリケートの公開 API の受入シナリオには、1vs3の結果が4配置分に対応し、論理グループの対応が保たれることが含まれる。その実装過程で配置生成を分離し、具体的な期待配置を用いた単体テストを追加することは候補となる。一方、生成処理を関数に分けるという実装上の都合だけで、実装前に人間がその関数のテストを個別承認する手順にはしない。

受入テストが一対局全体を扱う場合も、最初の実装変更だけで全 simulator を完成させる意味ではない。必要な内部処理を段階的に検証・実装し、最後に受入シナリオを満たす。自己生成結果だけから期待値を作らず、公開 API の結果と内部処理の期待値を区別する。

### Unresolved question

第134問で最初に選んだ開始前検証の具体例は、型設計の見直しによって未決である。公開 API の最小案を整合させ、その契約を直接確認できる最初のシナリオを選ぶ。型を弱めて不正な入力を受け付けたり、テストのためだけに内部の配置生成を公開したりしない。具体例の再選定や Rust 実装開始は、この説明だけでは承認済みと扱わない。

今回のテストリスト管理の相談を受け、[管理案と少数の候補](test-list.md)を別紙にした。候補の採用・実装順・実装開始は未承認であり、内部関数ごとの承認や全テストの先行列挙は要求しない。セッションを移るときの現在地は[引継ぎ](handoff.md)を参照する。
