# 公開 API の契約・利用シナリオのレビュー案

作成日: 2026-11-20。第1〜106問の合意を、呼び出し側から読める形にまとめる。根拠は[回答記録](questions.md)、ゲームの概念モデルとルール判断点は[設計案](design.md)、公式根拠の取得状況は[ルール差分](rule-differences.md)を参照する。

**confirmed requirement** は回答で合意した契約、**candidate design** は今回の整理・提案、**unresolved question** は未確定の判断である。この文書全体の承認、具体的な Rust の型・シグネチャの確定、実装開始を意味しない。説明用の項目名は公開 schema ではない。

## 1. 最初の提供範囲

### Confirmed requirement

- Rust API を先に提供する。Python API は将来の検討対象とする（第97問）。
- 最初の公式プリセットは雀魂の四人段位戦とし、東風戦・半荘戦を含める。適用版・細則は別途公式根拠で照合する（第62・63・98問）。
- 利用側が Agent と牌譜出力先を渡し、LizhiSim が複数卓の進行・互換な要求の集約・応答の照合を管理する（第1〜3・24問）。
- 同期型の実行 API は対局群と必要な終了処理の決着まで待ち、結果を返す。内部の Agent の回答は非同期とし、Future 方式を基本とする（第18・30・37・106問）。
- 通常の独立対局の実行に加え、比較グループの配置を展開するデュプリケートを扱う（第74問）。
- 標準の牌譜ファイル保存・読込みと、記録した入力・行動を使う replay を提供する（第27・105問）。
- 最初の統計補助は順位別回数とする。報酬と段位ポイントへの換算は利用側が担当する（第34・64・65問）。
- 一つのライブラリ crate から始め、将来の細分化を見据えて module の責務・依存方向を整理する（第101問）。

大会・シーズン・トーナメントの管理、Epsilon 型の局面分岐、production API での任意の途中局面指定は初期対象に含めない。開発用の局面設定は単体・リグレッション検証に用いる。外部の実牌譜取得・逐次照合は後続とする（第32・36・100問と追加のスコープ判断）。

## 2. 利用側が準備するもの

### Confirmed requirement

| 入力の概念 | 契約・用途 | 主な根拠 |
|---|---|---|
| 解決済みのルール | 一回の実行は一つのルールに統一する。プリセットからの個別変更を含め、LizhiSim が提供する値・振る舞いの選択肢を組み合わせる | 第31・70・71問 |
| 対局の開始条件 | 最初の局を配る前から開始する。開始持点は参加者ごとに指定可能。独立対局の初期席順は明示指定・seed によるランダム割当の双方を扱う | 第33・35・36問 |
| 比較対局の指定 | 比較グループ・席数配分・比較セット数を渡す。一グループに一つの Agent インスタンスを対応させる | 第74・93問 |
| Agent | 合法手から行動を選ぶ。推論・モデル入力変換・通信・内部の方策更新を担当する | 第2・7・8・38問 |
| 牌譜出力先 | 完了・中断した対局の完全情報の記録を処理する。標準の保存処理に加え、独自実装も利用できる | 第22・24・26・105問 |
| 実行全体の seed | 対局識別と牌山共有の識別を区別して、実行順に依存せず乱数入力を導出する | 第51・52・74・75問 |
| 実行の上限・期限 | 同時進行対局数、Agent ごとのバッチ件数・集約待ち時間、意思決定・通知・出力の期限を指定する | 第46〜50・85・89〜92問 |

LizhiSim はすべての開始条件と共通設定を開始前に検証し、不正があれば対局群を開始しない。将来の Agent 応答の正しさまで事前検証する契約ではない（第66問）。

意思決定・Agent 通知・牌譜出力の必要な有限期限は、コア API で明示指定する。規定値の補完は文書例や設定ファイルからの変換側の責務とする。出力受付待ちにも別の有限期限を設ける。具体的な入力形式・値の範囲・受付待ち期限の指定方法は未決である。

同じ Agent・牌譜出力先インスタンスを、並行する別実行で共有する契約は初期対象に含めない。別インスタンスが内部で共通の推論・保存サービスを使うことは可能とする（第99・102問）。

## 3. 対局実行の正常系

### Confirmed requirement

1. 利用側が開始条件・設定・Agent・出力先を準備し、同期型の実行 API を呼ぶ。
2. LizhiSim が開始前検証を行い、同時進行数の範囲内で対局を開始する。各対局・観測座席へ専用の開始通知を送り、その処理完了後に当該対局・座席の意思決定要求を渡す。
3. LizhiSim が合法手を計算する。一つだけなら要求を省略し、唯一の行動で進め、その経過を記録する。複数候補なら、互換な他卓の要求と集約して Agent の受付範囲内で渡す。
4. Agent が Future 方式で非同期に回答する。その間も独立した他卓を進める。バッチの回答は全件そろってから受け取り、要求識別情報の対応を検証してから行動を適用する。
5. 局末・対局終了は、意思決定がなくても Agent へ通知する。完了・中断した対局の牌譜を出力先へ渡す。終了通知・出力待ちの対局も同時進行数に含め、必要な終了処理の決着後に枠を空ける。
6. 実行を終え、対局番号順の結果一覧と対象となる統計を返す。実行全体の正常完了と、全対局の成功は区別する。

根拠: 第3・9・11・14〜19・30・37・50・55・56・82・85・88・103・106問。

同じ対局・観測座席の通知と要求は、先行処理の完了後に次を渡す。同じ Agent の呼び出し入口はすべて直列とする一方、受付範囲内で別卓・別席の処理や複数バッチの完了待ちを重ねられる。牌譜出力先も入口の直列化と受付後の処理完了を区別する（第15・16・73・86・89問）。

## 4. Agent との受渡し

### Confirmed requirement

| 情報・操作 | 契約 |
|---|---|
| 要求の文脈 | 対局・観測座席・要求を識別できる。共有 Agent 全体で一つの座席状態や履歴位置を使わない |
| ルール | Agent は、プリセット変更を含む実際の解決済み設定を参照できる |
| 入力 | 現在の観測状態、対局開始からの観測可能な全履歴、新規部分の開始位置、合法手一覧を渡す |
| 新規部分の基準 | 同じ対局・座席で処理完了した要求・通知の履歴末尾を基準とする |
| 入力の有効性 | 非同期処理中も要求時点の内容を維持し、受付時に全コピーすることを Agent に必須としない |
| 回答 | 要求識別情報と、選んだ行動そのもの、または要求単位の処理エラーを返す。回答一覧の順序は自由 |
| 抽選 | 行動を確率的に選ぶ場合も Agent 内部で行う |
| 経過の配送 | 開始通知、意思決定要求、局末・対局終了・中断の通知を用いる。すべての観測イベントの即時配送は要求しない |

根拠: 第7・10・14・19・54・55・58〜60・72・82・106問。各通知の具体的な入力・完了表現、履歴イベントの粒度は未決。

合法手は固定の行動番号・マスクではなく、その局面で選べる行動の一覧とする。同じエンジン・ルール版の同じ状態では順序も再現する。具体的な並び順は未決。立直と宣言牌は一行動、チー・ポンとその後の打牌は別要求とする。手切り・摸切り、赤牌・通常牌は区別し、手牌内の同種・同属性の牌の個体差では打牌候補を増やさない（第8・54・67〜69・80・81問）。

同じ応答窓に要求した全席の回答を待ち、到着順ではなくルールで競合を解決する。他家の未公開選択を同じ窓内の後続要求へ漏らさない。異常時まで無限に全席を待ち続ける契約ではない（第53問）。

### Candidate design

**C-API-01: Future の完了結果としてバッチの回答一覧を受け取る。** Agent が共有の回答領域を書き換え、Future が完了だけを通知する方式と比較する。完了結果に回答をまとめる案を第一候補とすれば、完了前の回答の読み出しや共有領域の書戻しを API で抑えやすい。これは第106問の Future 採用から自動的に確定する判断ではない。

### Unresolved question

Future の具体表現・実行基盤・所有と借用は未決。受付での Agent の独占を処理完了まで継続させて複数バッチを受け付けられなくする設計は、合意した重複処理と整合しない。受付と Future の進行・完了、受渡し時刻の具体的な境界をレビューする必要がある。

通知・出力の完了表現にも同じ Future 方式を使うかは、Agent の意思決定回答とは区別して検討する。Future の待機を打ち切ることと、推論・通信・保存を停止してデータを回収することも別の契約である。

## 5. 比較セット・乱数・記録

### Confirmed requirement

| 比較形式 | 一セットの配置数 | 完全な一セットで各グループが得る順位結果の件数 |
|---|---:|---|
| 1vs3 | 4 | 4件・12件 |
| 2vs2 | 6 | 各12件 |
| 各1席の4グループ | 24 | 各24件 |

グループ内の入替えを別配置として増やさず、一グループに対応する Agent は一インスタンスとする。統計は比較グループに属する全参加席の結果を合算する。全配置の最終順位が確定した比較セットだけを統計対象とし、不完全なセットは終了済み配置の分も含めて除外する。各対局の結果・牌譜は残し、除外を識別可能にする（第74・77・78・93問）。

同じセットで場を含む局番号・本場が一致する局には、同じ牌山を必要時に生成する。通常の山順と席別ツモ列は実験設定で選ぶ。席別の列が尽きれば、残り枚数が最多の他席の列の末尾から取得する。同数時の具体的な優先順、列の割当・山と王牌の整合の詳細は未決である（第75・76・94問）。

列の枯渇による取得は、どのツモでどの席の列から取得したかを発生ごとに完全情報の牌譜へ残す。対局結果には有無・回数を付け、Agent 向けの観測・履歴・通知にはこの識別情報を含めない。異なる行動列でも各席の全ツモが最後まで固定される保証はしない（第94・95・104問）。

各局の実際の牌山、採用した行動、ルール・取得方式と必要な意味版を記録し、replay は記録入力を直接使う。同じエンジン・ルール意味版では、対応する OS・CPU 間でも麻雀上の再現性を保証する。Agent の確率的選択、実時間や期限切れの発生、対局間の出力順は対象外とする。RNG・seed 導出・shuffle は未選定である（第7・27〜29・51・76・96問）。

標準の保存・読込みから replay まで提供するが、具体的な符号化・ファイル構成・圧縮は未決。第29問を越える将来版での全過去記録の互換性は確定していない（第105問）。

## 6. 成否・期限の契約

### Confirmed requirement

| 発生したこと | 影響範囲・返す情報 | 主な根拠 |
|---|---|---|
| 開始前の入力・共通設定が不正 | 対局群を開始せず設定エラーとする | 第46・66問 |
| 要求に対応する行動が合法手にない、または要求単位の処理エラー | 該当対局を中断し、他卓を続ける。自動的な代替行動を選ばない | 第12・19・20問 |
| Agent のバッチ全体のエラー・期限切れ、回答の識別情報の不備 | 同じ Agent インスタンスを使う進行中の対局をすべて中断し、それを使う未開始対局を開始しない。識別情報に不備があるバッチの回答は一部も適用しない | 第21・39・56問 |
| Agent の通知エラー・期限切れ | 該当する進行中対局は中断。終了済みの得点・順位は維持し、通知の失敗を別に記録する | 第41問 |
| 通知の失敗に伴う中断 | 失敗した対局・座席にも中断通知を一度試みる。通知を自動再試行せず、中断通知の失敗から中断通知を繰り返さない | 第83・84問 |
| 出力エラー、出力処理または受付待ちの期限切れ | 実行全体を中断し、全体エラーと部分結果を返す。確定済みの得点・順位と出力成否を区別する | 第25・42・43・92問 |
| 利用側からの停止要求 | 新規対局を開始せず、進行中対局を中断し、途中牌譜・中断通知等の終了処理へ進む | 第44・45問 |
| 個別の失敗を含む対局群の処理終了 | 全体中断の理由がなければ実行全体は正常完了。各対局の結果・失敗・未開始等は結果一覧で区別する | 第103問 |

意思決定期限は Agent へバッチを渡した時点から計測する。集約待ち・受付待ちは含めない。牌譜出力も受渡し時から処理期限を計測し、受付待ちは別の有限期限で扱う。Agent の受付待ちの制限や通知期限の起点等は未決である（第47〜49・90・91問）。

結果一覧は完了・中断・未開始を含め対局番号順とし、出力成否を別に示す。牌譜の配送は番号順を保証しない。全体中断時にも、全配置の最終順位が確定したセットの統計を返す。記録出力に失敗した場合の保存成功やプロセス強制終了からの復旧は保証しない（第43・79・87・88問）。

## 7. ルール判断とゲーム進行の境界

### Candidate design

公開 API の利用例から内部の責務へ落とすため、次の判断点を分けてレビューする。具体的な型・呼び出し構造は未確定である。

| 判断点 | ルールに応じて決まること | 進行側が守ること |
|---|---|---|
| 合法手 | 立直・鳴き・槓・見送り・流局時の申告等の選択可能性 | 許可された候補だけを要求へ含める |
| 状態遷移 | 宣言・成立・公開等の適用順序、槓や流局等の分岐 | 牌・状態・履歴を整合した単位で更新する |
| 行動の解決 | 和了・副露の優先、複数回答の採否、見送りの効果 | 到着順をルール上の優先順位にしない |
| 局終了 | 和了、通常流局、途中流局等の成立条件 | 終了理由を残し、必要な公開・申告から精算へ進む |
| 連荘・次局 | 親の継続、局番号・本場・供託の更新 | 局条件と牌山共有キーを整合させる |
| 対局終了 | 規定局数・延長・飛び・終了の優先関係 | 通常の対局終了と管理上の中断を区別する |
| 得点・最終精算 | 支払・丸め・供託・順位・終了時の精算 | 二重徴収・二重精算を防ぎ、結果と記録を対応させる |

一つのルールの完成を先行させても、これらの差を数値設定だけで表せるとは仮定しない。他の指定ルールの調査を使って境界を検討し、未確認の公式値は埋めない。

## 8. 最初の受入例

### Candidate design

以下は既存の合意を通して読むための受入例であり、網羅的な unit test list や実装順の確定ではない。具体的な局面・牌山・期待点数は公式根拠と独立した期待値から必要時に作る。実牌譜を大量取得することは前提にしない（第36・100問）。

| ID | 入力・状況の例 | 外部から確かめる振る舞い |
|---|---|---|
| AC-01 | 有効な開始条件・決定的な検証用 Agent・メモリ出力先で複数卓を実行する。東風戦・半荘戦は別実行で扱う | 開始通知、意思決定、局末・終了通知、出力を経て番号順の結果を得る。唯一の合法手の経過も履歴に残る |
| AC-02 | 同じ Agent が別卓の複数バッチを受け付け、片方の回答を遅らせる | 入口は直列、受付後の待機は重複可能。入力は不変。他卓を進め、同じ卓・座席の先行処理の順序は守る |
| AC-03 | 1vs3・2vs2・各1席の4グループをそれぞれ一比較セットで実行する | 配置数・グループ別件数が5節の表と一致する。同じ局条件の牌山を共有し、全配置が最終順位を持たないセットは統計から除外する |
| AC-04 | 一つの要求の不正行動と、別のケースでの回答識別情報の不備 | 前者は該当対局のみ、後者はその Agent の対局群へ影響する。識別不備のバッチから部分適用せず、途中記録を残す |
| AC-05 | 出力先が受付を制限し、保存処理を遅らせる。別のケースでは受付待ちを期限切れにする | 終了処理待ちも対局枠を保持する。受付待ちと受渡し後の期限を分け、受付待ちの期限切れは全体中断・部分結果の返却となる |
| AC-06 | 席別ツモ列の枯渇を起こす、開発用の決定的な入力 | 最多列の末尾から取得し、牌譜の発生記録と対局結果の有無・回数が対応する。Agent 向け情報へ識別情報を混ぜない |
| AC-07 | 標準保存した記録を読込み、Agent の再推論なしで replay する | 実際の牌山・採用行動を再実行し、同じ意味版で局面・精算・結果を照合できる。対応 OS・CPU 間の検証方法も具体化する |

この表の期待する振る舞いは各回答の契約に基づく。検証用 Agent の具体実装、通知・期限の競合を制御するテスト支援、保存形式等は未決であり、今回は作成・実行していない。
