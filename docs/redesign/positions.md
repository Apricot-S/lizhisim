# 外部指定局面からのsimulation

2026-09-28のユーザー追加要件。区分は[再設計レビュー案](README.md)に従う。Rust型・API・入力schemaは確定しない。

## 1. Confirmed requirement

- 外部から特定の局面を指定し、その続きから実行できる（CORE-009）。配牌からの実行だけを入口にしない。
- 同じ局面を基点に、残り牌山をランダムにした複数試行で期待値を評価する用途を支える。
- AI学習のために外部で生成した局面を開始点として扱う。
- 山の残り部分をあらかじめ設定するか、その生成方法・分布をどうするかは局面生成側が判断する（CORE-010）。simulator内部で未指定部分を勝手にshuffleする契約にはしない。
- 指定局面も外部入力として検証し、通常実行と同じルール意味論・情報秘匿・決定性を保つ。開始局面以後を再生できる（DATA-010）。

これらは局面生成器や期待値集計器を今回実装する指示ではない。外部生成器がsimulatorの公開された入力境界を利用できる設計を対象にする。

## 2. 利用例と参考資料

### 特定局面の期待値評価

指定した局面の固定部分を保ち、生成側が条件に整合する残り牌山等を各試行へ供給する。simulatorが各試行を継続し、評価側が点数差、順位、和了率等の目的変数を集計する候補とする。

「期待値」は指定局面だけでは一意に決まらない。固定する情報、未指定の他家手牌等を補う分布、残り山の分布、agent方策、終了・打切り条件、評価量に依存する。これらを実験条件として記録する案とし、分布や評価量をsimulatorの既定ルールとして選ばない。

### 学習用局面の生成

ユーザー提示の[TadaoYamaoka「麻雀AIを深層強化学習で作る その６(初期局面生成)」](https://tadaoyamaoka.hatenablog.com/entry/2023/10/27/235405)（公開2023-10-27、確認2026-09-28）は、役を持つ手牌から牌を交換し、河・副露・立直・牌山も含む開始局面を作る例を示す。役や向聴を意識した学習用分布から開始する用途の参考とする。

記事の生成アルゴリズム、確率分布、近似、特定実装のAPIをLizhiSimの仕様として採用するものではない。また公式麻雀ルールの出典ではない。

## 3. Candidate design: 生成と受入の境界

```text
外部の局面指定・制約・生成方針
  -> 局面生成側が各試行の入力を具体化
  -> simulatorの局面入力境界で検証
  -> 検証済みの局面から通常の純粋遷移・要求/応答へ合流
  -> 試行結果と再生記録
  -> 評価・学習側で集計
```

| 責務 | 担当候補 | 内容 |
|---|---|---|
| 局面分布・固定条件 | 外部の局面生成側 | 役・向聴・巡目等の学習条件、固定する情報、試行ごとの差分 |
| 未知部分の具体化 | 外部の局面生成側 | 他家手牌、残り牌山、補充領域等をどの分布で補うか |
| 牌資源の受渡し | 生成側とsimulatorの境界 | 全列を開始時に渡す案と、必要な境界で外部供給する案を比較。事前固定の要否は生成側の方針 |
| 入力検証・再開 | Simulator | phase、牌保存、rule、台帳、資格、必要な履歴文脈を検証し合法な進行状態へ変換 |
| 合法手・遷移・終局・精算 | Simulator | 通常実行と同じ計算を使用。局面指定専用の簡略ルールを作らない |
| 期待値・学習目的 | 外部の評価・学習側 | 方策、評価量、試行数、打切り、統計・報酬の集計 |

部分情報だけを指定した局面条件と、実際に一試行を進めるのに十分な入力は区別する。simulatorが未指定情報をどの確率分布で補うかを決める機能は要求しない。遅延供給を採用する場合も、未供給の牌を使う遷移の前で外部入力を要求し、確定した供給内容を検証・記録する候補とする。具体的な供給protocolはQ-13で未決。

## 4. Candidate design: 局面に必要な文脈

見えている牌姿だけでは合法手や点数を再現できない場合がある。下表は必要情報の検討リストであり、必須fieldの確定schemaではない。

| 領域 | 検討する情報・整合性 |
|---|---|
| Ruleと対局 | 不変rule版、人数、座席、親、場・局位置、本場、得点、供託。対局終了まで走らせる場合の対局文脈 |
| 再開phase | 取得前、取得後、打牌への反応待ち等。actor、直前の原因、取得牌と由来 |
| 牌の所在 | 手牌、副露と構成・供給元、河と鳴かれた履歴、北抜き、通常山、王牌・補充領域・表示牌。参照を二重加算しない |
| 資格・履歴 | 立直の宣言中/成立、フリテン、見送り、一発、第一巡、槓や北抜き等による資格変化、責任払いに必要な事実 |
| 未完の処理 | 応答窓の原因、成立前の宣言、未確定の支払い・公開・補充。受入対象とするphaseの範囲は未決 |

入力の構造・牌数が整合すること、将来の判定に必要な文脈が十分なこと、合法な開始からその局面へ到達できることは異なる保証である。毎回の全履歴提示を必須にすると合成局面の用途を狭める。一方、任意flagを無検証で通すと不正な学習データを作る。履歴要約の検証、履歴による到達性検証、その保証区分をどう扱うかをQ-13に残す。不足した資格を一律falseにして受理しない。

入力用の意味表現と、内部snapshotやRust memory layoutは別の境界とする候補を置く。外部から内部状態を直接書き換えるAPIを前提にしない。既存実装の非公開constructorを外すことだけでは、この要件を満たさない。

## 5. Candidate design: 反復実行とreplay

基点局面を不変の入力として保持し、試行ごとに牌資源・外部応答・識別子を分ける案とする。基点へ戻すためにconsumedな継続を再利用せず、各試行を検証済み開始条件から独立に作る。内部のclone・共有・copy-on-writeは未選定。

開始記録には局面schema、基点ID/hash、rule版、具体化された状態、必要な履歴要約、検証保証、試行ID、供給された牌資源または再構成情報を残す候補とする。生成器の版・seedだけに依存せず、生成器なしでも当該試行を再現できる記録を検討する。遅延供給の入力も順序・原因とともに記録する。

過去の配牌や行為を実行したことにする架空のevent列は作らない。外部指定局面をログの開始根拠とし、そこから先のcanonical eventと状態hashを比較する。通常実行の途中と等価な入力なら、同じ継続入力で将来の結果も一致する契約を候補とする。過去のevent prefixや試行IDまで同一であることは要求しない。

局面生成側が完全情報を持っていても、agentへ渡す観測はその座席の情報だけに射影する。未指定の他家手牌等を補った試行の結果は、その補完分布に条件付けられた結果であり、公開情報だけから唯一決まる値と見なさない。

## 6. 検証候補とunresolved question

| 検証候補 | 守る契約 |
|---|---|
| 通常進行の途中と等価な局面を外部指定し、同じ後続入力を与える | 将来の合法手・意味event・終端状態が一致する |
| 基点局面を固定し、生成側が異なる残り牌山を与える | 各試行を独立に実行し、記録から個別に再生できる |
| 同じ具体化済み局面と入力を異なるworker数で実行する | 試行結果がscheduleから独立する |
| 枚数超過、二重所在、phase不整合、必要な資格文脈の欠落を与える | 理由を区別して拒否し、暗黙に修正・補完しない |
| 立直・槓・北抜き・見送り後の生成局面を与える | 牌姿だけで資格を推測せず、ruleに沿った合法手を得る |
| 合成局面と履歴から復元した局面を記録する | 来歴と検証保証を混同せず、架空の過去eventを作らない |

**Unresolved question:** Q-13で受入phase、最小文脈、到達性の保証、完全/遅延供給の境界を比較する。期待値の評価条件はQ-07・Q-10、保存と互換性はQ-08、crate配置はQ-11と連動する。外部指定局面を受け入れることと生成方針を生成側へ置くこと自体は未決に戻さない。
