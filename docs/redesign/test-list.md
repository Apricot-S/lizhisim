# テストリスト

作成日: 2026-11-20。現在は **candidate design** としての管理案と候補リストであり、第152問で採用した一件を除き、実装順は未決である。[公開 API の契約](api-contract.md)と[回答記録](questions.md)を根拠とする。

## 作成と管理の案

- 公開 API の利用シナリオから、外から確かめられる振る舞いを一件ずつ書く。仕様の根拠、入力の概略、期待する振る舞いを記し、候補と採用済みを区別する。
- 最初から全仕様のテストを列挙しない。次に扱うシナリオと、その実装・不具合調査で必要になった項目を少数ずつ追加する。
- 公開 API の受入シナリオを起点にする。内部の単体テストは、その実現に必要な責務や境界条件が分かった段階で追加する。全内部関数のテストを着手条件にしない。
- 型で不正を表せなくできる場合、実行時エラーのテストを作るために型を弱めない。内部構造や同じ条件式をなぞるだけのテストを増やさない。
- 外部から見える仕様の未決事項だけを、必要な時点で人間に一つずつ確認する。既存契約に沿う内部テストの追加・分割・命名を、その都度の承認事項にはしない。
- 一件を実装するときは、必要なテストの失敗確認、最小実装、成功確認、必要な整理を行う。受入シナリオが大きければ必要な内部テストを段階的に進め、受入テストの成功まで追跡する。
- 固定牌山・局面・精算の期待値は必要時に独立した根拠から用意する。自己生成結果をそのまま期待値にしない。具体的な期待値と詳細はテストコード・fixture に置き、本文には目的と契約を残す。
- リストは仕様資料・テストコードと同じ Git で管理し、対応する変更で更新する。完了した行も検証先へのリンクとして残す。

## 状態の案

仕様の採否と実装状態は分けて記録する。

| 項目 | 値と意味 |
|---|---|
| シナリオの採否 | 候補／採用済み／撤回。対象の仕様が確定していても、このテストの範囲・順序まで採用済みとは限らない |
| 実装状態 | 未着手／着手中／検証済み／保留。未実装・未実行の項目を成功扱いにしない |
| 着手中の証拠 | 実際のテストファイル・テスト名、失敗の確認結果、残る作業を必要な範囲で追記する |
| 検証済みの証拠 | 実際のテストへの相対リンク、実行コマンドと結果を追記する。コードの所在・期待する契約はコードと同期する |

「検証済み」はその時点で該当テストを実行した記録であり、以後の全環境・全変更に対する保証ではない。CI の対象になった項目は CI でも継続検証する。機能追加時に失敗した既存項目を、過去の成功だけで完了扱いしない。

## 当面の候補

既存の[受入例](api-contract.md#8-最初の受入例)から三件だけを追跡候補にした。順番は実装順ではない。第152問で TL-002 を最初の受入テストに採用した。四人の通常実行で、対象席の開始通知が完了するまではその席に意思決定要求を渡さず、完了後に最初の要求が届くことを確認する。実装は未着手。配置生成の内部単体テストを最初にする第150問の案は撤回済み。

| ID | 種別 | 根拠 | 入力・外から確認する振る舞い | 採否 | 実装状態 | 具体化に必要なこと |
|---|---|---|---|---|---|---|
| TL-001 | 公開 API の受入 | AC-01、第3・18・30・82・145問 | 有効な四人の通常実行で、Agent の通知・意思決定・牌譜出力を経て、対応する対局結果を返す | 候補 | 未着手 | 最小 API、正常系の具体的な入力と独立した期待結果。東風戦・半荘戦を一回の実行で混在させない |
| TL-002 | 公開 API の interaction | AC-02、第16・82・112・152問 | 開始通知が未完了の対局・座席に意思決定を渡さず、完了後に要求を渡す。最初は四人の通常実行の一席を対象とする | 採用済み | 未着手 | 完了を制御できる検証用 Agent と、待機・停止を確実に終えるテスト手順。中断通知の例外を通常通知と混同しない |

初期の網羅率目標・全テスト一覧・テストフレームワークの追加は今回決めない。既存 Rust のテストがあることを、新設計の検証済み扱いにしない。
