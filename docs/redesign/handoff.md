更新日: 2026-11-20。セッションの会話を再現する代わりに、現在地と再開先を示す。作成時のブランチは feat/brand-new、直前のコミットは 65ccd17（docs: record redesign decisions through question 150）。再開時には Git の現在の状態を確認し、この値を作業ツリーの最新状態と決め付けない。

## 最重要の制約

- **Rust の実装開始は未承認**。テストソース・コンパイル可能な試作・依存追加もまだ行わない。
- ゼロからの再設計であり、旧コード・型・crate・旧 Accepted ADR は調査資料。CI・toolchain・ライセンス等は可能な限り維持する。
- 公開 API の契約・利用例からトップダウンに仕様化し、実装開始後は TDD。内部部品のテストを先に一式作る方式へ変更しない。
- 設計質問は一度に一つ。回答を記録して反映する。確定要件・候補・未決を分け、採用済みの同じ判断を再質問しない。
- 不正入力のテストを作るために型や API を弱めない。既存契約に沿う内部テストや局所的な実装判断を毎回の承認事項にしない。
- ユーザー変更と Git の index を保全する。指示なしに stage・commit しない。

## 最新の合意の要点

| 対象 | 合意 |
|---|---|
| 実行 API | 公開の実行呼出しは同期。通常実行とデュプリケートは別 API、内部実装は共有する |
| 通常実行 | 席順は内部でランダム化。比較セットの全配置展開・牌山共有は行わない |
| 別の実験 API | 固定席・指定牌山・途中局面からの実行は通常 API と分ける方針。具体仕様・初期提供は未決。開発用局面 fixture は必要 |
| Agent 構成 | enum で閉じた構成を表す。四人は4者独立・1vs3・2vs2、三人は3者独立・1vs2。通常実行でも全構成を指定できる |
| デュプリケート | 四人の4者独立は24配置、1vs3は4配置、2vs2は6配置。セット内の同じ場を含む局番号＋本場で牌山を共有。完全なセットのみ順位統計へ入れる |
| Agent の型 | 人数型をパラメーターにした一つの Agent trait。観測・合法手・回答・登録も四人／三人に応じた型にする。具体型・識別子は未承認 |
| 本体と論理枠 | Agent 本体を一度登録し、構成内の固定長配列から登録先を参照。同じ本体を複数枠で使える。論理参加者・グループや統計を本体の同一性で併合しない |
| 所有・受付 | 本体は呼出側が所有し実行中だけ貸す。本体は Send。意思決定・通知・出力の受付は &mut self、入口は直列 |
| 非同期完了 | 返す Future は Box 化して型を消去し、Send とする。必要なデータを独立して保持し、本体や一時入力を借用し続けない。受付後の処理は重複可能 |
| 入力保持 | Agent は正常完了後も入力を保持でき、保持量・期間は Agent が管理。取消で参照データを無効化しない |
| 失敗・期限 | 有限期限をコアで明示指定。Agent の受付待ち・回答期限切れはその本体を使う対局群に影響。通知の待機・処理失敗は該当対局だけ。詳細は6節 |
| 出力・停止 | 利用者停止では既存期限内で牌譜保存を続ける。出力先故障では追加送信を止め、未完了出力へ取消を伝える。全体失敗は Result のエラー側、開始後の失敗には部分報告を含める |
| 同時進行上限 | NonZeroUsize を使い、0の実行時エラーを作る案は撤回した |
| 初期範囲 | Rust API、一つのライブラリ crate。最初の公式プリセットは雀魂四人段位戦の東風戦・半荘戦。報酬と段位ポイント換算は利用側。順位別回数の補助を提供する |
| 再現・記録 | 同じ意味版・設定・seed・採用行動で対応 OS/CPU 間の再現性。Agent の確率的選択・実時間の期限発生は保証外。牌譜は実際の牌山・採用行動・進行イベント等を保存し Agent なしで再実行する |
| 標準形式 | 人間可読 JSON 系、一対局一ファイル、無圧縮・圧縮を提供。通常再生は形式と進行の意味の双方が互換な版で許可する。具体 schema・RNG・codec は未決 |

これは引継ぎの要約である。細部の採用範囲・失敗や統計の例外は元の回答記録・API 契約を参照する。

## 撤回済みの案を再提案しない

- 最初のテストとしての明示席順の重複。通常 API は明示席順を受け取る前提ではない。
- 同時進行上限0を run に渡してエラーにするテスト。NonZeroUsize で排除する。
- 四人の人数配分1＋2の不一致を作るテスト。構成を enum で限定する。
- 内部の1vs3配置生成の単体テストを、公開 API 起点の最初の TDD に必須とする案。必要ならデュプリケート API の実装時に検証する。

第134問で開始前検証を最初に選んだ記録はあるが、その具体例はすべて撤回済み。別の最初のシナリオを採用したわけでもない。合意していない正常系への切替や、内部部品からの着手を決定済みにしない。
