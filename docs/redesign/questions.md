ユーザー指示（2026-11-17）により、仕様駆動で公開 API のトップダウンから設計し、TDD で実装する。利用シナリオ、外部から観察できる振る舞い、API 契約、受入例を順に具体化する。設計質問は一度に一つとし、回答を記録して依存する次の判断へ進む。詳細な内部設計や全 API の確定を先行させず、実装開始の指示を受けた後に合意した振る舞い単位で red → green → refactor を進める。

第2問への最終回答（2026-11-17）: agent 接続は **Agent trait の実装を渡し、LizhiSim が呼び出す** 方式とする。呼び出し側の手間を減らすことを重視し、LizhiSim が複数卓の互換な意思決定要求を集約して Agent に渡し、Agent trait はバッチ推論・通信を行って非同期に回答する。2026-11-19 に、要求集約とバッチ推論の責務をこのように明確化した。受付条件、バッチ上限、送信条件は未決。以前の「利用側が要求を取り出して応答を返す」選択を置き換える。第14問で、同じ Agent インスタンスを複数卓・複数座席で共有できることが確定した。trait の method signature、要求の受渡し単位、応答待ちと非同期の表現、並行呼び出しの契約は未決。

第3問への回答（2026-11-17）: 最初の対局実行 API は **指定した対局群の完了後に結果を返す方式（C）** とする。LizhiSim が呼出しの中で卓進行と Agent 呼出しを管理する。同期関数/async の選択、内部 worker・runtime、途中結果の提供、取消・一般的な失敗の扱いは未決。第12問で、不正行動時は該当対局だけを中断し、完了と失敗を区別して返すことが確定した。この選択で内部の並列実行や Agent によるバッチ推論を制限せず、バックグラウンド実行ハンドルを基本 API の前提にしない。

第4問への回答（2026-11-17）: 最初の一ルールを選ぶ前に、対象間の構造的な差分を調べる。四人は雀魂・天鳳・麻雀一番街の段位戦、最高位戦・連盟・麻将連合・協会・RMU（新決勝方式を含む）・Mリーグ・WRC、三人は雀魂・天鳳・麻雀一番街の段位戦を比較対象とする。四人/三人とも雀魂・天鳳の大会設定で可能な設定も含む。[対象一覧と初回調査](rule-differences.md)を参照。比較対象は確定したが、最初の実装順・適用版・初期 release の完成範囲は未決。

第5問への回答（2026-11-17、Q-15 解決）: **通常の simulation は合法行為のみ** とする。チョンボ、誤発声、多牌少牌等を発生させず、それらによるアガリ放棄・罰点・立直料返却・再競技は通常の状態遷移に含めない。Agent の不正応答は API 上のエラーとして扱い、麻雀の反則・罰点へ変換しない。公式の反則条項は対象外として追跡する。提示された合法手以外の行動への対応は第12問で該当対局の中断と他卓の続行に確定した。その他の API エラーへの対応は Q-09 で未決。ルールが合法と認める見送り・聴牌伏せ等を、反則の除外を理由に禁止する決定ではない。

第6問への回答（2026-11-18）: **聴牌伏せの可否をルール差分とする**。認めるルールでは、流局時に実際に聴牌し、強制公開等の制約に該当しない者に「開示して聴牌申告/伏せて不聴申告」の選択肢を提示する。認めないルールでは選択肢を出さない。天鳳・雀魂はユーザー指定により選択肢を出さない対象とする。立直者の公開義務と、立直者を他家より先に公開するか、残りの申告・公開を誰から行うかは別の規則として調査する。[公開順の調査結果](rule-differences.md)では、立直者先行の規定と、立直の有無にかかわらない席順の規定の双方を確認した。オンライン各サービスの公式本文による照合は、ユーザー指定とは別の証拠状態として追跡する。

第7問への回答（2026-11-19、Q-07・Q-08 の一部確定）: **Agent は選んだ行動を返す（A）**。確率的に選ぶ場合も抽選は Agent が担い、LizhiSim は行動分布を受け取って抽選する契約にしない。確率的な Agent が再実行時に同じ行動を選ぶことは LizhiSim の再現性保証外とする。同じ意味版・ルール・初期条件・具体化済み乱数入力・要求ごとの確定行動と管理入力からゲーム進行を再現することとは区別する。牌譜・replay には実際に採用した行動を残す。具体的な action 表現、記録形式、保証する環境・版の範囲は未決。

第9問への回答（2026-11-19、Q-07 の一部確定）: **合法手が一つしかない意思決定点では Agent への意思決定要求を省略する（A）**。LizhiSim が唯一の合法手で進行し、その行動も牌譜に記録する。省略した場面を含む経過は、第10問で合意した観測可能な全履歴に含める。配牌・点数精算等、もともとプレイヤーの選択ではない内部処理とは区別する。

第10問への回答（2026-11-19、Q-07 の一部確定）: **現在の観測状態と対局開始からの観測可能な全履歴を渡し、新規部分の開始位置も示す**。A を基本とし、全履歴を使う Agent と、mjai Agent 等のようにイベントを順に処理する接続の双方を想定する。全履歴と差分を二重にコピーすることは要件にしない。合法手が一つで要求を省略した場面の経過も履歴に含める。新規部分の開始位置は、同じ対局・同じ観測座席の履歴に対応させ、共有 Agent 全体で一つの位置にはしない。具体的なインデックス表現、前回のどの配送時点を基準にするか、初回・再試行・再接続時の扱い、履歴の参照寿命・イベント粒度は未決。Agent に許可されない情報は履歴にも含めない。

第15問への回答（2026-11-19、Q-02 の一部確定）: **Agent が示す受付可能な範囲で、複数バッチを処理中にできるようにする（A）**。各バッチは複数卓の互換な意思決定要求をまとめたものであり、前のバッチの完了前でも Agent が受け付けられれば次のバッチを渡せる。Agent は受付範囲を一バッチに制限することもできる。LizhiSim は受付範囲を守り、Agent 内部での実際の並列実行は要求しない。同じ対局・同じ座席の通知と要求の順序は第16問で LizhiSim が保証することに確定。受付範囲の具体的な表現・予約・解放、呼び出し入口を複数スレッドから同時に実行してよいかは未決。

第17問への回答（2026-11-19、Q-02 の一部確定）: **一つのバッチ内の回答は、バッチ全体がそろってからまとめて受け取る（A）**。Agent は回答の一覧をまとめて返し、LizhiSim は部分回答によって同じバッチの卓を先行再開しない。異なるバッチは第15問の受付範囲内で並行して処理できる。バッチ単位で回答を受け取ることと、各対局の成功・失敗の扱いは別であり、第12問の不正行動時の対局単位の中断は維持する。回答一覧と要求の対応の具体表現、第19問で確定した要求単位の処理エラーの具体表現、バッチ全体の失敗・期限切れ時の扱いは未決。

第18問への回答（2026-11-19、Q-02・Q-07 の一部確定）: **対局群の実行 API は、Agent の対局終了通知の処理完了まで待ってから戻る（A）**。正常に完了した実行では、API が戻った時点で対象の Agent が終了通知を処理済みであり、通知を渡しただけの状態で呼び出し側に処理完了待ちを委ねない。Agent・通信資源の所有や終了処理そのものを LizhiSim に移す決定ではない。通知失敗・期限切れ・対局中断時の扱い、完了の具体的な通知方法は未決。

第21問への回答（2026-11-19、Q-09 の一部確定）: **Agent がバッチ全体の処理エラーを返した場合、その Agent を使う対局をすべて中断する（B）**。処理中の別バッチや、そのバッチに要求を含まない進行中の対局も対象とし、その Agent を使う未開始の対局は開始しない。影響を受けない Agent だけで構成された対局は続行する。影響範囲は第14問の共有 Agent インスタンスとの対応で判断し、同じモデル名だけを根拠に別インスタンスへ拡大しない。途中牌譜の保存は第22問、中断通知は第23問で確定。記録・通知の具体形式、処理中バッチの取消と遅延応答、未開始の記録、期限切れ時の扱い、自動再試行の有無は未決。

## 外部指定局面を採用する場合の検討材料

Q-12 は履歴上の追加要求を見落とさないための項目である。採用候補は次のとおり。

- 生成側は固定部分と未知部分を補う分布を決め、試行ごとの具体的な入力を供給する。simulator 内で残り山を暗黙に shuffle しない。
- 受入側は phase、牌保存、actor、対局文脈、立直・見送り・一発等の履歴文脈、未完の宣言・応答窓を検証する。構造的整合と合法な開始からの到達性は別の保証とする。
- 同じ基点を不変に保ち、各試行は独立に開始する。試行 ID・具体化した牌資源・応答を記録し、開始局面以後を再生する。架空の過去イベントを生成しない。
- 通常進行中の状態と等価な局面に同じ後続入力を与えた場合、将来の合法手・意味イベント・結果が一致することを検証候補とする。

受入を配牌後など少数の境界に限定する案は検証しやすいが用途が狭い。宣言中・反応待ちも受け入れる案は柔軟だが、未完の処理と台帳の整合条件が増える。今回はどちらにも確定しない。

## レビューの完了と次段階

今回の資料は G-01〜G-10、設計案の10節、履歴の H-ID、不変条件候補 I-ID、判断待ち Q-ID を対応付けて読む。採用する案には根拠と対象範囲を記録し、変更した場合は影響する節・不変条件・質問を同時に更新する。

初期スコープと主要な意味上の契約が合意されても、それだけで Rust 実装開始とはしない。実装の開始はユーザーの指示を待つ。採用が必要になった段階で、必要な設計決定や開発手順、test list だけを作る。
