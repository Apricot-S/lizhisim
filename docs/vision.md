# ビジョンとスコープ

## 1. ビジョン

LizhiSim は、深層学習モデル同士を大量かつ再現可能に対戦させるためのリーチ麻雀シミュレーターである。単一卓のゲームエンジンに留まらず、ルールが異なる卓を束ね、段位戦、リーグ戦、チーム戦、トーナメントを一つの実験として実行できる基盤を目指す。

最適化の中心は画面表示や人間の待ち時間ではなく、次の三点に置く。

1. ルール上の正しさと差異の追跡可能性
2. 多数の非同期な卓から GPU バッチ推論を作るスループット
3. 実験結果を説明・再生できる決定性

## 2. 解決する問題

麻雀では、各卓が同じ速度で意思決定点へ到達しない。ツモ切り、鳴き、連荘、流局、長い半荘などにより卓ごとの進行は非同期になる。同期的な `step()` を卓ごとに呼ぶ構造では、GPU に渡す推論要求が細切れになり、同時応答が必要な鳴き判定の扱いも不自然になる。

また「ルール」は一枚岩ではない。卓内の和了・点数規則、半荘の終了条件、大会の集計方式、段位ポイントの更新は別々に変化する。これらを分離しなければ、プリセットの複製が増え、どの差が結果を生んだか説明できなくなる。

LizhiSim は、純粋な状態機械が要求を発行して中断し、外側のスケジューラが要求を集約して応答を返す構造と、版管理されたルール合成でこの二つの問題を解く。

## 3. 想定利用者

- 自己対戦で方策・価値モデルを学習する研究者
- 複数モデル、複数ルール、複数大会形式を比較する評価担当者
- リーチ麻雀のルール差分を機械検証可能な形で管理する開発者
- 段位戦やリーグ戦を含む母集団シミュレーションを行う研究者

## 4. 主な利用シナリオ

### 4.1 大規模自己対戦

数千以上の論理卓を進行し、意思決定要求をモデル、入力 schema、デバイスごとにまとめて GPU へ送る。終了した卓は即座に新しい対局へ差し替え、遅い卓が全体を止めない。

### 4.2 クロスルール評価

同じモデル群を M リーグ、WRC、オンライン三麻など複数の不変プリセットで評価し、卓内成績と大会成績を分けて比較する。

### 4.3 段位戦の母集団シミュレーション

参加資格、マッチング帯、順位ごとの段位ポイント、昇段・降段を版管理された方針として実行し、母集団分布の推移を調べる。

### 4.4 リーグ・トーナメント評価

選手またはチームの登録、対戦カード、座順、ポイント持越し、足切り、勝ち上がり、同点処理を構成し、有限の大会全体を再生可能なイベント列として得る。

### 4.5 ルール回帰検証

公式資料の改定に対し、旧プリセットを不変のまま残して新しい版を追加し、差分に対応する golden scenario だけを明示的に変更する。

## 5. 設計原則

### 5.1 Correctness before throughput

誤った対局を高速に生成しても学習データとして価値がない。まずルールと決定性を検証し、計測後に表現や割り当てを最適化する。

### 5.2 Illegal states are unrepresentable

「ツモ前なのに打牌できる」「四人卓に三人分の順位点しかない」といった矛盾を、実行時の任意フィールドではなく型と設定検証で拒否する。

### 5.3 Functional core, imperative shell

合法手生成、局進行、精算、順位計算は副作用のない計算にする。非同期 runtime、キュー、時刻、乱数源、GPU、永続化は外側に置く。

### 5.4 Requests, not steps

公開 API は環境を一手進める操作ではなく、要求と応答の流れを扱う。複数応答を待つ鳴き窓も一級の中断点として表現する。

### 5.5 Version everything that changes meaning

ルール、プリセット、観測、action、イベント、乱数アルゴリズム、大会方針に版を持たせる。実験記録には可動 alias ではなく解決済み ID と内容 hash を残す。

### 5.6 Evidence over assumptions

プリセット値は公式資料または明示された補助資料に基づく。確認できない値を「一般的なルール」で埋めない。

## 6. 対象範囲

- 四人・三人リーチ麻雀の局、半荘、精算
- 版管理されたルールプリセットとカスタム設定
- AI の観測、合法手、意思決定要求、応答検証
- 複数卓スケジューリングと GPU バッチ推論用キュー
- 段位・レーティング、リーグ、チーム戦、トーナメント
- seed、牌山、応答、イベントによる記録と再生
- 学習用 trajectory と評価指標の出力

## 7. 当面の対象外

- Gym/Gymnasium 互換 API
- 人間向け GUI、演出、音声、チャット
- 公開オンライン対戦サーバーとアカウント管理
- 実卓の自動卓操作、発声品質、見せ牌、所作、服装などの完全再現
- 公式サービスへ接続するクライアントや非公開プロトコルの模倣
- 賭博、金銭、賞金の管理
- 不正行為検出

物理競技の罰則はルール出典として追跡するが、AI が常に合法 action を返す通常シミュレーションでは発生させない。大会運営上の加減点は、管理イベントとして別途表現する。

## 8. 成功の測り方

機能完成だけでなく、以下を継続計測する。

- 公式プリセットごとの監査済み項目率と未解決差分数
- 既知牌譜・scenario の一致率
- seed と応答列からの replay hash 一致率
- 1 秒あたりの局数・意思決定数
- 推論 batch size 分布、GPU 利用率、要求待ち時間の p50/p95/p99
- 論理卓あたりのメモリ量
- キャンセル、重複、期限切れ、不正応答の発生率

数値目標は、正しさを満たす walking skeleton のベンチマーク後に ADR で決める。根拠のない初期目標は置かない。

## 9. Phase 0 の完了条件

- 要求、境界、用語、状態遷移、ルール構造、大会構造が文書化されている。
- イベント駆動、型付き継続、ルール版管理の ADR が Accepted である。
- 対象プリセットと公式出典の台帳があり、未確認事項が明示されている。
- t-wada TDD の手順、test list template、実装ロードマップがある。
- 旧実装と旧依存関係がリポジトリから撤去されている。
- 実装開始前の未決事項が [ロードマップ](roadmap.md) に集約されている。
